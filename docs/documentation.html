Fingerprints — Generic Fingerprint Modeling Platform

Design, Features & Testing

One generative fingerprint model that learns any event dataset (payments, service logs, deployments, incidents, infrastructure), reproduces statistically faithful synthetic data, anonymizes with per-field policies, and — as of this enhancement — exposes its versioned registry from the command line so changes between fingerprint versions can be inspected or gated in CI.

Overview

Fingerprints is controlled from a web workbench, Fingerprint Studio, backed by a FastAPI engine API. A fingerprint is a compact generative model of an event dataset: if it can generate data statistically indistinguishable from what it learned, one abstraction covers learning, recognizing, reproducing, and anonymizing data.

Learn

Schema induction + distribution learning from any event dataset, no per-dataset code.

Recognize

Score a journey's likelihood under a fingerprint — low likelihood flags novel/anomalous behavior.

Reproduce

Sample new, statistically faithful synthetic records.

Anonymize

Per-field policies swap sensitive fields for masked/synthesized equivalents.

Diff

Compare two fingerprints of the same entity across versions/time — the basis of this enhancement.

Quick start:

# no install needed if fastapi/uvicorn/sqlalchemy are present
python demo.py                                   # CLI: all five fingerprint types
python -m uvicorn api.main:app --port 8600       # Studio + API
# then open http://127.0.0.1:8600

Design

Core principle

A fingerprint is not a hash or a label — it is a compact generative model. Every source is normalized by a thin adapter into the same canonical shape before modeling, so the model itself never knows which domain it is in.

Canonical event model

Record = {
  entity_key   : groups records into a journey/session (UETR, trace_id, pod, txn STAN…)
  timestamp    : ordering + temporal model
  state_fields : fields whose combination defines a behavioral "state"
                 (service+status, log_template_id, k8s condition, ISO8583 MTI+RC…)
  attributes   : everything else — typed automatically
}

Adapters (parsing only, no modeling logic): ISO 20022 MX, SWIFT MT, ISO 8583, OTEL logs/traces, Kafka/Redis/DB/K8s metrics, CI/CD release events, incident tickets.

Anatomy of a fingerprint (five learned layers)

#LayerCaptures
1Schema profileInferred field types (categorical / numeric / identifier / timestamp / text) and per-entity uniqueness, with format patterns for identifiers.
2Field marginalsFrequency tables, empirical distributions, format patterns. Journey-constant fields (amount, currency, debtor) modeled once per journey.
3Conditional dependenciesPer-state distributions, e.g. latency_ms | state.
4Sequence modelMarkov chain over states per journey — the "execution path".
5Temporal modelStart-time window + inter-arrival distribution.

Plus a derived embedding signature so fingerprints can be compared, clustered, and searched. Five platform fingerprints (payment, service, deployment, incident, infrastructure) are five configurations of this same model — see DESIGN.md §4 for the full table.

Registry, matching & drift

Fingerprints are versioned artifacts in the registry (fingerprints/registry.py): every re-learn adds a version (pickle for the model object, JSON sidecar for its summary), so releases and drift can be diffed later. Fingerprint.diff(other) (fingerprints/model.py) compares two fingerprints of the same shape and reports:

  • states_added / states_removed — behavioral states seen in one version but not the other
  • transition_shifts — Markov-chain transition probabilities that moved by ≥ 2%
  • field_drift — categorical fields with total-variation distance ≥ 1%, or numeric fields whose mean moved ≥ 5%

This already powers the Studio's Registry tab ("deployment-style version diff") and the engine API's GET /api/v1/fingerprints/{name}/diff. The enhancement below exposes the same capability as a standalone command line tool.

Features

Fingerprint Studio workflow

  1. Connect — simulator, file upload (CSV/NDJSON), PostgreSQL table, or Bulk API batches; "Load & suggest binding" proposes entity key / timestamp / state fields.
  2. Learn — fits the fingerprint, versions it in the registry, runs the PII scan.
  3. Inspect — journeys/events/paths stats, execution-path fingerprints, per-field learned shapes.
  4. Mark PII / Policies — per-field policy (keep / drop / hash / mask / generalize / synthesize) with live before→after preview.
  5. Generate — synthesize or anonymize; volume as journeys or scale factor; fidelity report + zero-leak check; CSV download.
  6. Registry & Recipes — fingerprint versions, version diff, saved recipes with one-click re-run.

MT/MX & relational data

Format-generic MX (ISO 20022) and MT (SWIFT) adapters cover the full MT↔MX equivalence set (pacs.008/MT103, pacs.009/MT202, camt.053/MT940, pain.001/MT101, and more) with round-trip verification. On the Connect tab, "learn parent + child tables" fits relational data (parent primary key + child foreign keys) and generates FK-consistent synthetic datasets. A Bulk API (POST /api/v1/sources/{id}/batches) accepts NDJSON/CSV with idempotency keys for safe retries.

Production notes, backend comparisons (correlated vs. independent vs. SDV), and secrets configuration (FP_SALT, FP_API_TOKEN) are in README.md.

Enhancement: Fingerprint Registry CLI new

Why

The registry already tracked every version and the engine already knew how to diff two fingerprints, but both were only reachable through the Studio UI or the HTTP API. That makes them hard to use in a script, a pre-commit check, or a build pipeline. This enhancement adds fingerprints/registry_cli.py, a standalone command line tool built on the exact same Registry and Fingerprint.diff() objects, so:

  • a developer can see what changed between two fingerprint versions without starting the Studio;
  • a CI job can re-learn a fingerprint from fresh data and automatically fail the build if the shape of the data drifted unexpectedly (--fail-on-drift);
  • changes can be captured as a JSON artifact for later review (--format json).

No changes were required to the core engine — the CLI is a thin front end over Registry.list()/versions()/load() and Fingerprint.diff().

Manual CLI walkthrough

To see it work against real, non-synthetic-test data:

# 1. populate the registry with a couple of versions per fingerprint
python demo.py

# 2. list what's registered
python -m fingerprints.registry_cli list

# 3. see what changed between the two most recent "payments" versions
#    (run demo.py again first to create a new version to diff against)
python -m fingerprints.registry_cli changes payments

# 4. same, machine-readable, for piping into another tool
python -m fingerprints.registry_cli changes payments --format json

# 5. simulate a CI gate failing on drift
python -m fingerprints.registry_cli changes payments --fail-on-drift; echo "exit=$?"
Note: demo.py appends a new registry version on every run (this is existing behavior, unrelated to the CLI), so running it twice is the quickest way to get two versions to diff manually.

Command line usage

The CLI ships two equivalent entry points:

Adapting it

  • Replace the python demo.py "re-learn" step with however this pipeline actually produces a fresh fingerprint version (an ETL job, scripts/seed_postgres.py, a nightly export) — everything downstream (CLI report + gate + artifact publish) is unchanged.
  • Scope the gate to specific fingerprints instead of --all by naming them, e.g. registry_cli changes payments --fail-on-drift, if only some fingerprints should block the build.
  • Drop --fail-on-drift (keep only the JSON report step) for a report-only pipeline that never fails the build, just surfaces drift for review as a downloadable build artifact.
  • The same commands work unmodified in GitHub Actions, Jenkins, or a local pre-push hook — the pipeline file is Azure DevOps-flavored YAML, but nothing about the CLI itself is ADO-specific.

Enhancement: E2E Test tab new

Tab 7 in the Studio, E2E Test, drives a simulated payment end to end across the systems a real transaction would pass through, so a tester can see — system by system — how the message is built, translated, and relayed, without a single real system being involved.

Design

One payment travels through an ordered chain of systems as ISO 20022 messages. Every hop keeps an explicit field-level lineage (mapped / generated / enriched / passed through / regenerated) instead of a black-box transform, so clicking any system shows exactly what it changed. Three ways to seed a run

SourceWhat happens
Complete syntheticEvery message is freshly generated (account/amount/currency optionally overridden). Always available, no external dependency.
File upload by systemUpload a real message for any system in the chain; any system left blank still derives its message from the previous hop, so partial real data can be tested alongside simulated fill-in.
Connect to system databaseThe origination system's payment instruction (account / amount / currency) is pulled from a configured read-only table instead of being randomly generated; the rest of the chain is still simulated (see the "never touch production" principle in the Roadmap).

N systems, not just 4

The four systems above are the default chain, not a hard limit. The Studio's "+ Add intermediary system" control inserts any number of extra systems (Fraud Check, Sanctions Screening, a correspondent bank hop, …) at any position in the chain. The engine decides where the one format-changing step (pain.001 → pacs.008) actually happens by role, not position — an intermediary inserted before Payment Processing still relays the plain pain.001 message; conversion happens exactly once, at whichever system is tagged role: "processing". Everything else (enrichment, message-id regeneration, the response leg) already works over an arbitrary-length chain.

Reviewed messages are editable, with confirmation

Clicking Preview 1 sample always generates exactly one end-to-end message set and renders it — that single sample is what gets reviewed. The System detail panel's transformation table and raw XML are the "review" step; below them, every field of that hop's message is shown in an editable table, with three kinds of correction:

  • Change a value — edit the text in an existing field's row.
  • Remove an optional tag — click Remove on its row (the row shows struck through; click again, now labeled Undo, to change your mind before applying).
  • Add an optional tag — type its path and a value under + Add optional tag (a bare name like CdtTrfTxInf.Purp.Cd is auto-prefixed with the message's root segment, so you don't have to know the full ISO 20022 path by heart) and click the button; the new row appears marked new.

Clicking Apply edit & re-run pops a confirmation dialog listing exactly what will change (including remove <field> for dropped tags) before anything happens — accepting it re-runs the sample with those corrections applied on top of the message, and every hop downstream of the edited one re-derives from the corrected message: an added tag is carried forward the same way a real optional field would be, and a removed tag stays gone. Changed fields show a red edited badge, added ones an added badge, and removed ones a removed badge in the lineage table, so a reviewer can immediately see what was manually corrected versus what the engine produced (fingerprints/e2e.py's _apply_edits: a field value of None in an edit means "remove this tag").

Two independent axes, easy to conflate: Flow type is which payment this is (Outward, RTGS, Book Transfer, …) — a chain of systems and a message shape, previewed one sample at a time. Volume is how many message sets of that flow type to actually generate — a separate Generate control, covered below, that is never "1 to 50 for a quick look" and "thousands for real testing" — it is always the same file-based generation path, whether you ask for 1 or 50,000. Picking a flow type never implies a count. Edits confirmed on the sample stay scoped to that preview — a generated volume is always freshly, independently derived per message set, never stamped with a one-off manual correction.

User-definable flow types

The four built-in flow types (Outward, Inward, Outward Return, Inward Return) are just pre-registered instances of one shape: {chain, origin_message_type}. + Add flow type… defines a new one on the fly — name it (e.g. "FAST", "RTGS", "Book Transfer", "Telegraphic Transfer"), pick a base pattern:

Base patternorigin_message_typeBehavior
Customer-initiatedpain.001.001.09Like Outward: converts to pacs.008 at whichever system has role: "processing".
Received pacs.008pacs.008.001.08Like Inward: pacs.008 all the way through the chain.
Returnpacs.004.001.09Like Inward Return: pacs.004 all the way through the chain.

— then build its chain with the same editor used for intermediary systems, including dropping systems entirely (e.g. a Book Transfer that never leaves the bank can skip Clearing & Settlement). No real-world RTGS/FAST specifics are hardcoded — you configure the shape; the engine doesn't special-case the flow type's name anywhere, only its declared origin_message_type and chain (fingerprints/e2e.py's scenario_def parameter).

Preview one sample, then generate volume

The Studio deliberately offers only two controls, not a spectrum of batch sizes to pick between:

ControlCountWhere results goPurpose
Preview 1 samplealways exactly 1Rendered live: pipeline diagram + editable System detailReview a representative message set, correct it if needed, confirm it looks right
Generateany number you specify — 1, 1,000, 50,000Written to files (NDJSON + CSV + manifest), downloadableProduce the actual volume needed for testing/verification, once the sample is trusted

There is no in-between "render 50 flows live in the browser" mode — that was tried and dropped: it conflated "which payment is this" (Flow type) with "how many" (Volume), and a live-rendered medium batch wasn't the right shape for either reviewing (1 is enough) or bulk testing (needs to scale to tens of thousands, which the browser can't render anyway). See Bulk export & the CLI below for how Generate actually writes files at any scale.

Per system, the source is a choice between two kinds of data, used by both Preview and Generate:

  • Test dataset — upload an .xml file with several <Document> messages for one system (File upload by system source). Message set i uses that system's message i from the file (cycling if the generated volume is larger than the dataset) — useful for replaying a fixed set of real or hand-crafted test cases through the rest of the chain.
  • End-to-end dataset — leave a system without an upload and it keeps deriving its message from the previous hop, for every set — useful when only one system's real test cases matter and the rest of the chain should just behave normally around them.

The two can be mixed freely: e.g. a real test dataset for IBNK Channel with Payment Processing, CoreBanking, and Clearing & Settlement all still deriving end-to-end for every set/flow.

Bulk export & the CLI

fingerprints/e2e_cli.py and POST /api/v1/e2e/export both call the same fingerprints.e2e.export_flows — one generation path, so CLI and Studio output are identical. It streams: iter_batch() yields one flow at a time (not a Python list of all of them), so memory stays flat whether count is 10 or 200,000 (fingerprints.e2e.MAX_EXPORT). Measured: 50,000 flows across the default 4-system Outward chain (400,000 hop messages, ~400 MB NDJSON) in well under 10 seconds on a laptop.

python -m fingerprints.e2e_cli export --scenario outward --count 50000 --seed 1

python -m fingerprints.e2e_cli export --scenario inward --count 5000 \
    --account SG00OCBC0000004242 --out-dir data/outputs

# a custom flow type, from an inline JSON definition
python -m fingerprints.e2e_cli export --scenario rtgs --count 20000 \
    --scenario-def '{"label":"RTGS","origin_message_type":"pain.001.001.09",
                      "chain":["ibnk-channel","payment-processing","clearing-settlement"]}'

python -m fingerprints.e2e_cli list-scenarios

How to test through the UI

  1. Start the Studio: python -m uvicorn api.main:app --port 8600, open http://127.0.0.1:8600.
  2. Click tab 7 · E2E Test.
  3. Pick a Flow type (Outward / Inward / Outward Return / Inward Return, or a custom one — see below) from the dropdown.
  4. Leave Source on "Complete synthetic", optionally set a seed/account, and click Preview 1 sample.
  5. The Pipeline card renders two rows of clickable system nodes (Forward, Response). Click any node — the System detail card below shows its Forward-leg and Response-leg tabs, each with a field-by-field transformation table (color-coded: mapped / generated / enriched / regenerated / passthrough / edited) and a collapsible raw XML view.
  6. Scroll to Edit this message: change a field's value, click Remove on an optional tag's row (its input strikes through; the button becomes Undo), and add a new one via + Add optional tag (e.g. name CdtTrfTxInf.Purp.Cd, value SALA) — then click Apply edit & re-run. A confirmation dialog lists exactly what will change (including any removal); accept it and the sample re-runs with your corrections, every hop after this one now reflecting them (check a downstream system's detail to confirm the removed tag stays gone and the added one is carried forward).
  7. To try file upload by system: switch Source, upload an .xml message against any system, Preview again — that system's hop uses your file instead of a derived one (shown with a generic before/after diff, since there's no schema mapping to trace for a caller-supplied message). Upload a file with several messages and it becomes that system's test dataset when you Generate a volume (see below).
  8. To try database mode: switch Source, enter a read-only DSN and table name, Preview again — the origination message's account/amount/currency come from that table's first row.
  9. Click + Add intermediary system…, name it (e.g. "Fraud Check"), pick where to insert it, and Preview again — the new system appears as its own node and, if inserted before Payment Processing, visibly still carries the pain.001 message rather than pacs.008.
  10. Click + Add flow type…, name it "RTGS", pick base pattern 1 (customer-initiated), and edit its chain (e.g. remove CoreBanking) with the same insert/remove chips — Preview to see your custom flow type work exactly like a built-in one.
  11. Once the sample looks right, scroll to Generate volume, set the count to e.g. 5,000, click Generate — a summary (message-type and verdict counts) and three download links appear once it's done (typically well under a second per thousand message sets). Note that generated sets are freshly derived, not a copy of the edited sample — edits are a preview-only review tool.

Automated tests

tests/test_e2e.py (38 tests) covers: all four built-in scenarios' hop shape and message types; the explicit pain.001→pacs.008 field mapping; the pacs.002 response correctly correlating back to the original UETR/EndToEndId; configurable verdicts (ACSC/RJCT); lineage completeness and enrichment on every hop; XML rendering for every hop in every scenario; file-override behavior; N-system custom chains with an inserted intermediary (including the before/after-conversion boundary); the role-based fallback when no "processing" system exists in a fully custom chain; validation errors (too-short chain, duplicate ids, unknown scenario, missing database config); deterministic output for a fixed seed; field edits cascading downstream (including on the origin and response hops, and confirming an edit on one leg doesn't leak into the other); adding an optional tag and removing one, propagating correctly downstream, mixed with a value correction in the same call, and a no-op when removing a tag that was never present; live-preview batches (unique flows, per-system dataset cycling mixed with end-to-end derivation, and the 1–50 count bound); user-definable flow types via scenario_def (all three base patterns, chains that drop systems entirely, rejecting an unsupported message type); and bulk export (iter_batch matching run_batch, NDJSON/CSV/manifest correctness, cleanup on a failed export, and the count bound). tests/test_e2e_cli.py (9 tests) covers the same export path from the command line, including inline and file-based --scenario-def, custom chains via --chain/--system, and a local --file test dataset.

Roadmap

Where the E2E Test tab goes next. This is a planning view, not a committed schedule — column widths are relative (six upcoming periods), not calendar dates.

Guiding principles

This tool must never touch a production system. Every source (synthetic, file, database) is designed to be safe by construction: synthetic data never leaves the process, file upload only ever reads what the tester hands it, and database mode is scoped to read-only, explicitly-configured non-production tables. As this evolves, any new connector must keep that guarantee — for example by allow-listing DSNs and refusing anything that resembles a production host, the same way anonymization policies in this platform are already irreversible by design.

Test data starts at the requirements phase, not a production copy. The field mappings in fingerprints/e2e.py (e.g. pain.001 → pacs.008) are hand-written from the ISO 20022 specification today. The intended direction is to derive them from a checked-in, reviewable requirements artifact (an interface control document / mapping spec) from day one of a project, so the test data's lineage traces back to a signed-off requirement rather than to whatever a production system happened to be doing. That also means the tool is usable before the real systems exist — the whole point of an E2E test harness for a system still being built.

ADO integration path (Phase 2)

Mirrors the pattern already established for the registry (see Azure DevOps integration above):

  1. Add fingerprints/e2e_cli.py, a command-line runner over e2e.run_pipeline() — the same function the Studio's API calls — so a scenario can run headless: python -m fingerprints.e2e_cli run --scenario outward --format json > run.json.
  2. Add an E2ERegressionGate stage to azure-pipelines.yml that runs all four scenarios on every merge and diffs each run's hop message shapes against a checked-in "golden" fixture — the same drift-detection idea as registry_cli changes --fail-on-drift, applied to message shape instead of fingerprint statistics.
  3. Publish each run's per-hop XML and lineage JSON as a build artifact (PublishBuildArtifacts@1), so a reviewer can open exactly what the pipeline saw without re-running anything locally.
  4. Once Phase 4 lands, gate merges to interface-mapping code on the E2E suite passing against the read-only pre-prod connectors, the same way the registry gate blocks a merge on unreviewed fingerprint drift today.

Other considerations

  • Scenario definitions as versioned artifacts. Once scenarios are spec-driven (Phase 3), version them in the same registry that already versions fingerprints, so a scenario change can be diffed the same way a fingerprint's drift is diffed today.
  • PII stays inside the existing policy engine. Anything pulled from a real (non-production) database in Phase 4 should be run through fingerprints/anonymize.py before it's displayed or stored, exactly like the Connect tab's PII scan — no new bypass path.
  • Golden-run regression, not just shape checks. Beyond message shape, compare lineage kinds hop to hop (e.g. "CoreBanking used to enrich 1 field, now enriches 3") so a reviewer sees behavioral drift, not just structural drift.
  • Access control on database mode. Before Phase 4, DSN input should move from free text to a small allow-list of named, pre-approved connections (mirroring how FP_API_TOKEN already gates the API) so a tester can't accidentally type in a production connection string.
  • Reuse, don't reinvent, the fidelity report. A future "does the synthetic flow still look realistic" check can reuse fingerprints/fidelity.py's KS/TV-distance machinery against a batch of E2E runs, the same way it already validates bulk synthetic data.
